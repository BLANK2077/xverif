## session 实现与验证边界

临时目录 `<tmp>/npi-code-session` 中新增 `session.py`，保留原 demo v2 的查询实现与 27,227,705 字节索引，未重新提取 NPI、编译 fixture 或修改仓库源码。后台 Python 进程启动时执行一次 JSON 读取与 `Demo` 索引构建；之后所有客户端共享该内存对象。源码查询仍读取当前磁盘内容。

这次持久化的是从 NPI 提取的**离线代码索引**。它没有创建长期运行的 NPI 原生上下文，也没有验证真实 NPI handle 跨请求的生命周期。正式 xdebug 仍应在既有 C++ engine/session 内维护 CodeNavigationService，不照搬临时 Python daemon。

协议为本机 UDS 上的 JSONL，管理操作 start/status/close，业务操作 query；batch 或 `session.Client` 可在一个连接中连续查询。服务串行执行查询，同时可接受多个客户端；空闲连接不独占服务。启动通过专用 pipe 返回 readiness，只有完成索引构建和 `listen()` 后才成功。错误不自动重启、重连或切换到单次查询入口；socket 路径已占用时明确拒绝，不删除既有文件。关闭只删除该进程自己创建的 socket。

主 session 首次启动耗时 0.680 秒，其中索引加载 0.594 秒。12 题校准和100题正式实验复用同一进程。另起的受控重放 session 启动耗时0.654秒，198条服务端查询后仍只有一次索引加载；它已显式关闭。重放服务末尾 RSS 为112,980 KiB（约110.3 MiB）；这是整个Python服务进程，不是纯索引字节数。

## 第25题：代理纠正了参考答案

原标准把 single_beat_pct=-1 当数学负数，预期一直走burst。两个代理独立指出：$urandom_range返回32位unsigned，与signed int比较时，-1会转换为32'hFFFFFFFF，因此-1与101都走single。此处两组判断正确，原标准错误。相关类型与符号规则有 [Accellera随机函数材料](https://www.accellera.org/images/eda/sv-ec/1818.html) 和 [表达式符号规则材料](https://accellera.org/images/eda/sv-ec/2161.html) 支持。

两组提交后，主线程在临时目录用host VCS X-2025.06-SP1独立编译并运行表达式探针；未重编或仿真AXI fixture。两种取值各1000次均选择single，显式signed cast对照结果为0；编译与运行均exit 0，耗时9.477秒：

    SIGNEDNESS_RESULT negative=1000 positive=1000 unsigned_compare=1 signed_control=0

这项探针只裁定表达式语义。其它并发、4KB边界和scoreboard漏检仍是源码条件推演，未因这一小探针而变成“已复现fixture故障”。两组Q025均4分；没有改写原rubric、调题、换数据源或要求代理按错误标准改答案。

勘误记录见 [rubric-errata.md](<tmp>/npi-code-session/hundred/rubric-errata.md)；源码见 [adjudication-probes/signedness_probe.sv](<tmp>/npi-code-session/hundred/adjudication-probes/signedness_probe.sv)；执行命令和结果见 [adjudication-probes/result.json](<tmp>/npi-code-session/hundred/adjudication-probes/result.json)。

## 对xdebug实施方案的影响

优先顺序由本轮证据决定：

1. **P1中落实索引归属和代际。** CodeNavigationService由已有design engine持有；scope索引只成功构建一次，值对象缓存受预算限制，NPI handle按请求释放。明确close/reload后失效，禁止每请求全量加载。
2. **P1保留编译证据。** scope、declared_in、实际参数绑定、原始记录与唯一声明口径、重复候选和完整计数必须可解释；不能用同path静默去重或取首条掩盖歧义。
3. **P2准确标记源码关系。** 先满足当前spec的NPI位置/范围/当前文件合同，明确macro调用点和受保护实现；不能把NPI implementation位置命名为已核实extern原型。
4. **独立研究extern与宏来源增强。** 在专用临时fixture验证NPI能否分别返回prototype/definition/macro-definition关系及范围，之后修订共享SourceSpan合同。当前demo缺口不能靠默默加任意文件读取参数、decompile生成正文或换工具变体补全。
5. **未来再验证混合工具收益。** AI显式选择结构查询定位和文本阅读，在新实验中独立测量；本轮两组保持隔离，没有用rg替demo答题。module/top浏览、任意文件搜索和预处理文本不自动加入第一期已定义API。

可执行的生命周期要求、所有权、预算失败和close/reopen测试已补入spec第16节A32–A38；extern/macro/top来源缺口列为后续独立准入探针。P1–P4仍未实施，未修改action目录、schema、handler、skill或产品测试。

## 解读限制

- 两组各一个代理样本，不是多seed随机化研究；任务耗时包含检索策略、阅读、推理和答案编写，不能全归因于工具。
- 100题包含相关子问题，分数不是100个独立随机样本。很多反例由题干给定，测量的是证据驱动的解释和推演，不等于无提示自动发现缺陷能力。
- Q091–Q095刻意测量编译数据库专有能力，必须与共同源码推理分开；demo因该优势取得高分不代表其所有代码理解更强。
- 只用demo的限制用于暴露API边界；实际产品可以由AI显式选择结构查询和文本阅读，但本实验不混合工具，不静默fallback。
- 保护源码、编译版本一致性、运行时factory/对象值/虚调用仍有明确边界。任何反例推导都不等于当前默认fixture已经复现失败。
- 上轮单次demo为v1；本轮持久session使用含实际参数绑定和保护检查的v2。跨轮任务时间差同时受版本和代理策略影响，纯session收益应看同v2的受控重放。

本轮100题虽有83题以多跳、情景或反例为主要形式，仍出现明显分数上限效应。扩大题量已检验更多具体语义，却没有产生强区分度。后续若要检验“更精准理解”，应另外冻结包含隐蔽变更、冲突版本、跨package同名、实际特化差异的独立临时任务，并用不泄露缺陷位置的诊断题、多次随机分组和盲评复核；这不是本轮已经执行的实验，也不需要现在修改用户源码。
